The Baseline — What Panem Does Today (Naive lag_7)

The starting point

Before this project, Panem made production decisions using the simplest possible rule: "bake the same amount you sold last week."

This is known as a Naive lag_7 model — the forecast for today equals what was sold exactly 7 days ago. No training, no parameters, no machine learning.

Why it's a fair baseline: Given bakery's strong weekly pattern, lag_7 already captures the day-of-week cycle reasonably well. Any model we propose must beat these numbers — otherwise it adds no value to the business.
⚠️ A MAPE of 78.4% means the average error is almost as large as actual sales. On holidays or special events, the Naive model fails completely — it has no memory beyond 7 days.

XGBoost — First Attempt with Gradient Boosting

First attempt

Our first approach was XGBoost — a powerful tree-based algorithm. We trained one model per branch-product combination (7 branches × 5 products), the same structure we use for all models.

  • Seasonality handled with lag features: lag_7, lag_14, lag_21
  • Day of week, holidays, and payday encoded as numeric inputs
How we pushed XGBoost:
  • L1 & L2 regularization (reg_alpha, reg_lambda) — to reduce overfitting on small per-product datasets
  • Walk-forward CV — 10 rolling 7-day windows
  • Hyperparameter tuning — learning_rate, n_estimators, max_depth with early stopping

ARIMA & SARIMA — Classical Time Series Models

Step 1 — ARIMA: the classical starting point

ARIMA is the standard first model in any time series project. Unlike XGBoost, it is built to understand the order of time — it does not need lag features added manually; the time structure is part of the math.

How we selected the order — AIC

We used auto_arima to search hundreds of (p, d, q) combinations automatically. It picks the order with the lowest AIC score: AIC = 2k − 2·ln(L) — it rewards a better fit but penalizes adding more parameters. The best model selected was ARIMA(2,1,2).

What p, d, q mean

  • p — how many past values the model looks back (auto-regression)
  • d — how many times the series is differenced to remove trend
  • q — how many past errors the model corrects for (moving average)
The limitation we hit: AIC penalizes complexity, so it never selected p=7 (which would look back 7 days to capture the weekly cycle). ARIMA has no built-in concept of weekly seasonality — it can only approximate it through many lag terms, which AIC rejects as too complex.

💡 What we could have explored: ARIMAX — adding lag_7 as an external variable to force the weekly signal into ARIMA. We chose to move to SARIMA instead, which handles this natively.

Step 2 — SARIMA: adding the seasonal layer

SARIMA extends ARIMA with a seasonal component (P, D, Q)₇. The subscript 7 tells the model that the pattern repeats every 7 days — Mondays relate to last Monday, Sundays to last Sunday.

What we discovered: Adding m=7 confirmed that the weekly cycle is the single most important pattern in our data. SARIMA now captures weekend peaks that ARIMA missed completely. MAPE drops from 58.2% → 56.9% — a modest gain, but the key insight is structural: the model finally "sees" that Saturday demand is consistently 2–3× higher than a Tuesday.

LightGBM & Prophet — The Two Finalists

Two approaches, one winner

We arrived at two strong candidates. We trained and evaluated both rigorously using walk-forward cross-validation (explained in 5.5).

LightGBM — How it works

Gradient boosting builds hundreds of small decision trees one after another — each tree learns from the mistakes of the previous one. The result is a very powerful model for tabular data with many features.

We used Tweedie loss — a special error function designed for count data where some days have zero sales. A standard loss function would punish zero-sale days too harshly; Tweedie handles this gracefully.

SHAP = how much each feature moved the prediction. lag_7 is #1 in every branch — confirming what SARIMA already suggested: last week is the best predictor of next week.

Prophet — The Chosen Model ★

Developed by Facebook, Prophet breaks the series into components: trend + weekly seasonality + yearly seasonality + holiday effects. It does not require stationary data or manual lag engineering — the time structure is built into the model itself.

How we configured it:

  • Added Mexican public holidays natively — Prophet treats them as special days
  • Added 3 external regressors: is_quincena, is_holiday, tavg (temperature) — signals that affect demand but are not in the sales history
  • Trained one model per branch-product pair — 35 models total, each learning the patterns of that specific location and product
  • Evaluated with walk-forward CV — 6 rolling 7-day windows, same as the other models

Key operational advantage: Prophet produces 80% confidence intervals — the operator sees not just a single number, but a range. "We predict 80 units, but it could be anywhere from 65 to 95." That range is directly what you use to decide how much buffer to bake.

5.5
Refinement — How We Improved the Model (and What Didn't)

Iterative optimization

Once we had our finalists, we applied four refinement techniques. Not everything improved — being honest about limitations is part of the process.

🔧 Outlier Handling

Days with sales more than 3 standard deviations above the average (special events, recording errors) were replaced by the rolling average of the surrounding 7 days before training.

MAPE without outlier handling
64.8%→51.8%↓ 13pp
MAE without outlier handling
13.10→10.85↓ 2.25

📡 External Regressors in Prophet

Prophet supports adding external signals directly into its formula. We added is_quincena, is_holiday, and tavg as regressors — the same features LightGBM already used — so Prophet could learn their direct effect on demand.

MAPE without regressors
57.9%→51.8%↓ 6.1pp
Acc ±20% without regressors
18.3%→20.3%↑ 2pp
Regressors added: add_regressor('is_quincena'), add_regressor('is_holiday'), add_regressor('tavg') — Prophet now knows paydays and temperature directly, not just through historical patterns.

🔁 Walk-Forward Cross-Validation

We used 10 rolling 7-day evaluation windows, moving forward in time. This guarantees we never use future data to predict the past. A simple train/test split gives overly optimistic results.

MAE with simple train/test split
5.20 (overfit)→10.85 (real)
Why did MAE go up? It didn't get worse — the earlier number was an illusion. Walk-forward gives the real production performance.

We searched for the best settings for both finalists.
